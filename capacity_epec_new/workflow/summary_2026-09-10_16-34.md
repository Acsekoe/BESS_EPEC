# Jacobi stalls on the price-selection gap; a least-cost planner benchmark is added

**Written:** 2026-09-10 16:34 CEST (UTC+02:00)
**Project:** `capacity_epec`
**Reference data:** `model/input/market_data_smoothed.json`
**Reference market setting:** energy-only, `DemandAdjustment = 0` (`rho = 0`)
**Reference MPEC relaxation:** relaxed KKT, complementarity epsilon `1e-6`

## Executive status

**Still no equilibrium, and this session found out exactly what stops the
iteration from finding one.** A plain 20-sweep Jacobi run at damping 0.25 from
the symmetric start climbs for six sweeps to **219.942 MW** and then freezes:
from sweep 7 onward the capacity residual is exactly `0.0000` and every sweep is
bit-identical. That zero is **not** an equilibrium. It is the run refusing to
move because each investor's MPEC proposes a step that its own embedded prices
value at **+366 to +644 EUR/day** while the honest reclear of the very same
capacity profile values it at **−2 057 to −2 882 EUR/day**. The `rho = 0` dual
multiplicity is worth **2 700–3 250 EUR/day** at this profile; the real gains
being chased are **5–9x smaller than that**. The search cannot climb a signal
buried under its own price noise.

Separately, a **least-cost storage expansion planner** was built
([`model/plan_least_cost_storage.py`](../model/plan_least_cost_storage.py)) to
supply a defendable neutral start. The efficient fleet is **186.97 MW /
561.90 MWh**. Its *total* is unique; its *siting* is not — N3 and N9 are exactly
interchangeable to the planner.

The Jacobi run was **stopped by the user at sweep 13**, before `run_model.py`
reached its final `audit_equilibrium` stage, so **the 219.942 MW point carries no
zero-proximal audit**. Nothing here is a certificate.

---

## 1. What was run

```
python model/run_model.py --update-scheme jacobi --damping 0.25 --max-sweeps 20 \
    --output-dir model/output/jacobi20_d025
```

Everything else is the reference default: symmetric 5 MW/node start at 3 h,
`rho = 0`, relaxed KKT with epsilon `1e-6`, no proximal penalty, no quadratic
costs, `--convergence-metric regret` at `1e-3` relative, multistart off,
`--refinement-starts 3`, 4 workers. Because multistart is off, each investor
gets exactly **two** candidates per sweep: the incumbent, screened by an exact
market clear, and one MPEC solve started from the incumbent. The driver ranks
both on **exact recleared profit** and keeps the better one.

| 7–13 | **0.0000** | **219.942** | **0.0** | 0.0 | False | screened / screened / screened |

Two things in that table matter more than the totals.

**`screened_feasible` is not a solve.** It is the label the driver gives a
candidate that was only *cleared exactly*, never solved as an MPEC. It winning
means the MPEC step was rejected in favour of standing still. That is happening
for I1 and I2 from sweep 2 onward — the run has been half-frozen since its
second sweep.

**`max_regret` collapsing from 63 438.97 to 0.0 is an artifact, not progress.**
Regret here is best-response profit minus incumbent profit. When the selected
best response *is* the incumbent, regret is 0 by construction. The driver does
not fall for this: `stable_sweeps` stays at **0** throughout, because
`all_best_responses_optimal` is False, so the run would have exhausted all 20
sweeps and exited non-converged. The metric is honest about its own status; a
reader skimming only the regret column would not be.

Cost: ~211 s per sweep. Sweeps 8–13 were provably identical repeats of sweep 7
(same state, deterministic solves), which is why the run was stopped.

## 3. Why it freezes — the number that matters

From `model/output/jacobi20_d025/starts_sweep_007.json`, the two candidates each
investor had at the 219.942 MW profile. Every figure is an exact market clear +
settle, except `embedded` which is the MPEC's own objective at its own solution.

| | incumbent, exact | MPEC embedded claim | *same profile*, recleared | embedded − exact | true value of the step |
|---|---|---|---|---|---|
| I1 | 3 242.90 | 3 608.91 (+366.01) | **361.10** | **3 247.81** | −2 881.80 |
| I2 | 75 063.46 | 75 707.29 (+643.83) | **73 006.40** | **2 700.89** | −2 057.06 |
| I3 | 59 421.05 | — solve failed — | — | — | — |

I1's and I2's MPECs both terminated `optimal` with a bound violation of ~9e-14 —
these are clean local solutions, not solver failures. They are simply optimising
against a price vector the market need not choose. I3's MPEC returned
`error: Cannot load a SolverResults object with bad status: error` after 6.2 s.

So the mechanism is precise: **the embedded/reclear gap (2 700–3 250 EUR/day) is
5–9x larger than the profit differences the investors are trying to resolve
(366–644 EUR/day).** Best-response iteration cannot work under that ratio, no
matter what damping or update scheme is used. Damping 0.25 did not cause the
stall and a different damping will not remove it.

This also puts a number on the case for positive rho. At `rho = 100`, measured
in [`summary_2026-09-10_13-17.md`](summary_2026-09-10_13-17.md), the same
embedded/reclear gaps were **0.00 / 6.33 / 30.27 EUR/day** — two orders of
magnitude *below* the gains being chased instead of one above them. That is a
quantitative argument for the regulariser, not an aesthetic one. It does not
change the separate finding that rho *selects* a branch rather than merely
smoothing one.

Nodal MW: N6 75.465, N8 57.096, N9 28.280, N3 17.151, and **8.390 MW each** on

empty (§5). They are residue of the symmetric 5 MW/node start that grew slightly
and that no investor has an incentive to clear away — capacity is a
non-negativity-bounded choice, and nothing in a best response forces a
withdrawal from a node that is merely unprofitable at the margin.

`individually_rational` is True at every sweep. The maximum absolute
primal–dual gap held at ~0.0023 EUR/day through sweeps 1–6, i.e. the embedding
itself was tight; the problem is dual *non-uniqueness*, not dual *inaccuracy*.

## 5. The least-cost planner benchmark (new)

The user's framing was right: this is the lower level with capacities freed.
[`model/plan_least_cost_storage.py`](../model/plan_least_cost_storage.py)
minimises

```
generation offer cost + storage degradation + annualised storage capex
```

over dispatch **and** nodal `X_power` / `X_energy`, subject to exactly the ISO's
constraints (nodal balance, PTDF line limits, generation capacity, SOC dynamics
and periodicity) plus the two constraints the investors face on capacity: the
2–8 h duration band and the nodal connection limit. At `rho = 0` with inelastic
demand this is a single **LP**, so minimum cost is maximum welfare and there is
one global optimum value — no audit needed, unlike everything else in this repo.

It calls `iso_market.build_market` on its own model rather than reimplementing
it, so it cannot drift from the game's operating model. That required one
additive change to `iso_market.build_market`: an optional `model=None` argument
that attaches the market to an existing model, which lets the capacity values be
Pyomo variables instead of floats. Default behaviour is untouched.

**Result** (`model/output/planner/summary.json`):

| | |
|---|---|
| Total | **186.9714 MW / 561.9046 MWh** (3.0053 h) |
| N3 | 41.7622 MW |
| N6 | 47.6382 MW |
| N8 | 55.7253 MW |
| N9 | 41.8457 MW |
| N1, N2, N4, N5, N7 | 0 (~2e-11) |
| Daily operating cost | 215 473.22 EUR |
| Daily capital cost | 3 773.67 EUR |
| Operating cost with **no** storage | 232 631.31 EUR |
| Operating saving | 17 158.08 EUR/day |
| **Net social gain** | **13 384.41 EUR/day** |
| Mean LMP, with / without storage | 37.2604 / 36.3959 EUR/MWh |

Nodal connection limits are 200 MW everywhere and are **slack** at the optimum,
so the placement is economics, not the cap — and the GNEP coupling constraint is
inactive at this point.

The mean LMP *rises* when storage is added. That is measured, not modelled
intent: storage lifts the depressed prices in the congested zero-price pockets
by more than it shaves the peaks, in mean terms across nine nodes and 24 hours.
It is recorded here as an observation, not an explained result.

### 5.1 Is the planner solution unique?

Two-slack face probe (scratchpad `probe_planner_face.py`): constrain total cost
to `C* + eps` and push each quantity to both extremes. A width that scales with
eps is a unique optimum blurred by the band; a width that ignores eps is a real
face.

| direction | width at eps = 1 | width at eps = 10 |
|---|---|---|
| **total MW** | **0.7099** | **5.4677** |
| N3 | 94.9865 (0 → 94.9865) | 111.1262 (0 → 111.1262) |
| N9 | 94.9865 (0 → 94.9865) | 111.1262 (0 → 111.1262) |
| N8 | 60.4862 (48.3210 → 108.8073) | 77.2313 (35.8392 → 113.0705) |
| N6 | 35.9755 (43.4027 → 79.3783) | 47.5513 (37.3951 → 84.9463) |
| N1 | 0.2566 | 1.9784 |

**The efficient total is pinned at ~187 MW** — the width tracks eps almost
linearly (7.7x for a 10x band). **The efficient siting is not** — N3 and N9 are
interchangeable *to the digit*, and every node's width is nearly eps-independent.
The IPOPT point reported above is the analytic centre of that face, which makes
it the most neutral single representative of it, but it is a representative and
not "the" efficient placement.

This is the same class of object as the game's degeneracy, arrived at from a
completely different direction: a convex problem with a unique value and a
non-unique argmin.

### 5.2 The equal split as a start

`model/output/planner/planner_equal_split_capacities.csv` divides the fleet
three ways (62.324 MW each). The split is a **convention, not a planner
result** — the planner installs a fleet and has nothing to say about ownership.
It is feasible for every investor by construction: the duration band is
scale-free and the nodal cap binds on the sum.

One exact market clear + settle at that profile:

| | profit EUR/day | storage surplus | generation rent | capex |
|---|---|---|---|---|
| I1 (merchant) | 2 239.78 | 3 497.67 | 0 | 1 257.89 |
| I2 (wind) | 73 493.15 | 3 497.67 | 71 253.37 | 1 257.89 |
| I3 (PV) | 88 530.28 | 3 497.67 | 86 290.50 | 1 257.89 |

All three are individually rational, which is the property a starting point most
needs. Note the three **identical** storage surpluses: this is the co-located
indifference again — the ISO cycles all three at their limits and the split of
storage revenue is mechanical, so the entire asymmetry between investors is
generation rent.

## 7. What was *not* done

- **No equilibrium was certified.** Nothing in this session brings the project
  closer to an equilibrium profile than yesterday.
- **No zero-proximal audit of the 219.942 MW point.** `run_model.py` runs
  `audit_equilibrium` after the sweep loop; the run was stopped at sweep 13, so
  that stage never executed. The point is an unaudited stalled iterate.
- **The game was not run from the planner split.** The equal-split file exists
  and is settled (§5.2); no Jacobi, Gauss–Seidel or audit has been started from
  it.
- **The planner was only solved at `rho = 0`.** The `--demand-adjustment-penalty-eur-per-mw2`
  flag exists and is untested at positive rho.
- **The planner face probe is not exhaustive.** It maximises and minimises six
  chosen directions; it does not enumerate the vertices of the optimal face, so
  "N3 and N9 are interchangeable" is a demonstrated exchange, not a complete
  description of the face.
- **I3's sweep-7 MPEC failure was not diagnosed**, only recorded. It could be a
  transient IPOPT failure or a structural one at that profile.

## Recommended next step

Run the same 20-sweep Jacobi at damping 0.25 **from the planner equal split, at
`rho = 100`**, and compare it against the run in §2 on one criterion only:
whether `all_best_responses_optimal` stays True and the embedded/reclear gap
stays below the profit differences being resolved. §3 predicts it should — the
gap falls from ~3 000 EUR/day to ~0–30 EUR/day — and if it does not, the
diagnosis in §3 is wrong and should be revised rather than defended.

```
python model/run_model.py --update-scheme jacobi --damping 0.25 --max-sweeps 20 \
    --demand-adjustment-penalty-eur-per-mw2 100 \
    --initial-capacities model/output/planner/planner_equal_split_capacities.csv \
    --output-dir model/output/jacobi20_planner_rho100
```

Two caveats to carry into it. Positive rho **selects** the congested branch
worth −45 173 EUR/day to I3 relative to `rho = 0`, so a run that converges under
rho has answered a modified question, and the modification must be reported.
And the planner start is a neutral *convention*, not a focal point of the game —
converging there would be evidence, not proof, and would still need the
unrestricted three-player audit that no run has yet passed.
